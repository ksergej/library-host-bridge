# FLOW-01 — CICS MQ Host Processing (Manual Transaction → MQ Triggering via CKTI)

> Project: **Library System (Java Spring Boot ⇄ MQ ⇄ z/OS Host / COBOL / DB2)**
>
> Goal: Replace the current **manual batch job launch** with a **CICS-based host service**.
> We do this in two stages:
> 1) **MVP (manual):** operator manually runs a CICS transaction (`LIBT`) that processes **one** request message from MQ and posts a reply.
> 2) **Automation:** enable **MQ triggering** + **CICS MQ Trigger Monitor (CKTI)** so processing starts automatically on message arrival.

---

## 1. Purpose & Scope

### In scope
- A CICS transaction (`LIBT`) that starts a COBOL program (`LIBMQCIC`) to:
  - MQGET one request from `LIB.REQ.TEST`
  - execute DB2 logic (borrow/return/active loans)
  - MQPUT the reply to `LIB.REP.TEST`
  - commit/rollback via CICS SYNCPOINT
- Preserve the existing integration contract:
  - **CorrelationID = request MsgId** in the reply (mandatory)
  - payload is XML-like request/response (existing format)
- Stage 1 manual invocation of the transaction from a 3270 session.
- Stage 2 automatic invocation via MQ triggering and CKTI.

### Out of scope (for this flow)
- Full CICS UI/menus, BMS maps
- CICS TSQ/TDQ usage
- Moving Spring Boot to different correlation strategy
- Production hardening (HA, scaling policies, full security model) — captured as follow-ups

---

## 2. Actors & Components

### Actors
- **REST Client** → calls Spring Boot
- **Spring Boot service** → puts request to MQ, waits for reply
- **CICS operator (MVP)** → manually runs transaction `LIBT` in CICS (stage 1 only)
- **CICS region** (`APPLID=CICSTS62`) → runs the host program
- **IBM MQ** (z/OS) → request/reply queues (+ later trigger/initiation queue)
- **DB2 for z/OS** → LOAN/BOOK/etc tables (as per existing host program)

### Components
- **MQ queues**
  - `LIB.REQ.TEST` (request queue)
  - `LIB.REP.TEST` (reply queue)
  - Stage 2: `CICS.INITQ` (initiation queue)
- **CICS resources**
  - `PROGRAM(LIBMQCIC)` — COBOL program (CICS enabled, MQ + DB2)
  - `TRANSACTION(LIBT)` — manual/triggered entry point
  - Stage 2: `TRANSACTION(CKTI)` (or equivalent trigger monitor) enabled and configured
  - (Optional depending on site config): `MQCONN(...)` resource for MQ adapter
- **DB2 package/plan** for the CICS program (site-specific; must be consistent with run-time)

---

## 3. Preconditions / Assumptions

- CICS region is running and reachable: `APPLID=CICSTS62`.
- MQ queue manager is available to CICS (adapter installed/active).
- DB2 attachment to CICS is available (program can execute SQL under CICS).
- Request/reply queues exist and are accessible from both:
  - Spring Boot (distributed / client channel)
  - CICS region (local MQ on z/OS)
- Queue message sizes fit existing buffers (e.g., 8K). If not, chunking/segmentation is a separate task.
- Security:
  - Stage 1: operator has authority to run `LIBT`
  - Stage 2: CKTI has authority to start `LIBT` and access MQ queues

---

## 4. Happy Path (Step-by-Step)

### Stage 1 — MVP (manual CICS transaction)

1. **Client → Spring Boot**
   - REST call arrives.
2. **Spring Boot → MQ PUT**
   - Spring Boot puts request message to `LIB.REQ.TEST`.
   - MQMD fields:
     - `MsgId` generated by MQ
     - `CorrelId` set as per current strategy (can be blank); the **reply** will use CorrelId=request MsgId.
3. **Operator → CICS**
   - Operator logs into CICS region (`CICSTS62`).
   - Operator runs transaction: `LIBT`.
4. **CICS starts program**
   - `LIBT` starts `PROGRAM(LIBMQCIC)`.
5. **LIBMQCIC MQGET**
   - MQOPEN `LIB.REQ.TEST` for input (no wait or short wait; for MVP: no infinite wait).
   - MQGET **one** message.
6. **LIBMQCIC business logic**
   - Parse request (existing XML-ish routing).
   - Execute DB2:
     - BORROW / RETURN / ACTIVE paths (as in current batch program).
7. **LIBMQCIC MQPUT reply**
   - MQOPEN `LIB.REP.TEST` for output.
   - Prepare MQMD:
     - `CorrelId = request MsgId` (**mandatory**)
     - `MsgId = MQMI_NONE` (let MQ assign new MsgId)
   - MQPUT reply payload.
8. **Commit**
   - `EXEC CICS SYNCPOINT` to commit MQ + DB2 changes atomically (site config permitting).
9. **Spring Boot receives reply**
   - Spring Boot reads from `LIB.REP.TEST` using selector `CorrelId=request MsgId`.
   - REST response returned to client.

### Stage 2 — Automation (MQ Triggering + CKTI)

Same as Stage 1, except step 3:

3. **MQ Triggering**
   - Request queue `LIB.REQ.TEST` has triggering enabled.
   - When the first message arrives (0→1 transition), MQ puts a trigger message into `CICS.INITQ`.
4. **CKTI reads initiation queue**
   - CKTI (trigger monitor) MQGETs trigger message from `CICS.INITQ`.
   - CKTI issues `START TRANSID(LIBT)` (or equivalent) in CICS.
5. **LIBT runs automatically**
   - Continue from Stage 1 step 4 onward.

## 5. Alternate Paths

### A1) No messages on request queue (Stage 1 manual)
- `LIBT` runs, program MQGET returns `MQRC_NO_MSG_AVAILABLE`.
- Program returns a small diagnostic response (optional) or ends with “no work”.
- No DB2 work performed.

### A2) Multiple messages pending
- MVP: process **one** message per invocation and end.
- Stage 2: `TRIGTYPE(FIRST)` + repeated triggers start new tasks as queue becomes empty/non-empty again.
- Follow-up (optional): allow processing N messages per run with a cap (e.g., up to 10) to reduce overhead.

### A3) Retry / poison message
- If parsing/DB2 fails for a message:
  - Rollback (`SYNCPOINT ROLLBACK`)
  - Put an error reply (still with CorrelId=request MsgId) OR route to a dead-letter/error queue (future enhancement).
- Optionally track retry count via MQ backout count / backout queue (future enhancement).

## 6. State Machine

### Host-side processing state (per message)
- **IDLE**
- **RECEIVED** (MQGET successful)
- **PROCESSING_DB2**
- **REPLY_PUT**
- **COMMITTED**
- **FAILED_ROLLED_BACK**
- **DONE**

Transitions:
- IDLE → RECEIVED (MQGET OK)
- RECEIVED → PROCESSING_DB2 (request recognized)
- PROCESSING_DB2 → REPLY_PUT (logic OK)
- REPLY_PUT → COMMITTED (SYNCPOINT)
- Any → FAILED_ROLLED_BACK (SQLCODE/MQRC/parse error)
- COMMITTED/FAILED_ROLLED_BACK → DONE

---

## 7. API Contracts

### MQ contract (unchanged)
**Request**
- Queue: `LIB.REQ.TEST`
- Payload: existing XML-ish request envelope
- MQMD:
  - `MsgId`: generated by MQ

**Reply**
- Queue: `LIB.REP.TEST`
- Payload: existing XML-ish response envelope
- MQMD:
  - `CorrelId = request MsgId` (**mandatory**)
  - `MsgId` new (assigned by MQ)

### CICS contract
- Transaction: `LIBT`
- Program: `LIBMQCIC`
- Input/Output: MQ only (no COMMAREA required for MVP)

---

## 8. Persistence Map

- DB2 tables: same as existing batch host logic (e.g., `LOAN`, `BOOK`, etc.).
- No new datasets required for MVP beyond program loadlib and CICS definitions.
- Stage 2 adds MQ objects:
  - `PROCESS` definition for CICS trigger
  - `CICS.INITQ` initiation queue

---

## 9. Idempotency & Retry Rules

- Current functional idempotency is “best effort”:
  - If Spring Boot retries the same logical request, host may apply it twice unless request contains a unique business key.
- MVP acceptance assumes:
  - Either upstream prevents duplicates, or duplicates are acceptable for the demo/test.
- Recommended follow-up:
  - Add request `request_id` in payload and store a processed-log table to enforce idempotency.

---

## 10. Failure Modes & Observability

### Failure modes
- MQCONN/MQOPEN/MQGET/MQPUT failures (non-zero `MQCC` / `MQRC`)
- DB2 failures (`SQLCODE != 0 and != 100` where applicable)
- CICS security failures (transaction not authorized, CKTI not authorized)
- Plan/package mismatch at runtime (DB2 -805/-818 etc.)

### Observability
- Write minimal diagnostics to:
  - CICS transient data / CSMT / log (site-specific)
  - Or plain DISPLAY statements captured in region logs (MVP)
- Include Correlation identifiers in logs:
  - request MsgId (hex) and reply CorrelId

---

## 11. Exit Criteria

### Stage 1 (manual MVP) — PASS when:
- Spring Boot PUT to `LIB.REQ.TEST` + operator runs `LIBT` manually
- `LIBMQCIC` processes exactly one message and puts a reply
- Spring Boot receives reply by `CorrelId=request MsgId`
- DB2 changes are committed (or rolled back on error) deterministically

### Stage 2 (automation) — PASS when:
- With triggering enabled, a message arriving on `LIB.REQ.TEST` causes:
  - trigger message in `CICS.INITQ`
  - CKTI starts `LIBT`
  - reply appears in `LIB.REP.TEST` without manual action
- Repeated requests continue to work without manual intervention

---

## Implementation Notes (non-normative)

- Start with Stage 1 to validate:
  - CICS program runtime (DB2 attach + MQ attach)
  - queue names, security, plan/package correctness
- Only after Stage 1 works, enable triggering:
  - prefer `TRIGTYPE(FIRST)` for controlled starts
  - configure CKTI to run continuously (auto-start at region start via PLTPI if available)
