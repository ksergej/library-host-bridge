# Спецификация PROJECT\_CONTEXT\_COMMIT

Этот документ определяет протокол логических коммитов **`chit`** для использования в чатах с ассистентом.
Он описывает, как представляются чекпоинты (checkpoints) и как должны интерпретироваться
мета-команды `chit`.

Цель — эмулировать лёгкую текстовую систему контроля версий для контекста чата
(**chat git → `chit`**), чтобы можно было делать снимки состояния проекта, просматривать их
и логически откатываться.

---

## 1. Общие правила

1. Слово **`chit` должно стоять строго в начале строки** (без пробелов перед ним),  
   чтобы строка считалась командой `chit`.

2. Все команды `chit` — это **мета-команды для ассистента**, а не shell-команды.
   Они управляют тем, как ассистент:
   - создаёт и обновляет логические чекпоинты,
   - перечисляет чекпоинты,
   - логически откатывается к предыдущему чекпоинту.

3. **Чекпоинт** — это структурированный текстовый блок, фиксирующий логическое состояние проекта
   в некоторый момент чата.

4. Чекпоинты **привязаны к конкретному чату**.  
   Они определяются, просматриваются и сбрасываются только внутри текущего чата.

5. `chit log` по возможности должен **не менять текущий логический контекст ассистента**:
   это операция только чтения (просмотр истории).

6. `chit reset` выполняет **логический откат**, а не физическое удаление:
   - предыдущие сообщения чата остаются,
   - но ассистент должен считать действительной базой только активные чекпоинты (до точки отката).

---

## 2. Формат блока чекпоинта

Каждый чекпоинт ДОЛЖЕН иметь следующий формат:

```text
=== CHECKPOINT: <NAME> ===
PROJECT: <Название проекта>
ID: <последовательный числовой ID>
TIME: <YYYY-MM-DD HH:MM:SS>   # локальное время пользователя или наилучшее приближение
SCOPE: <краткое описание того, что фиксирует чекпоинт>
=== END HEADER: <NAME> === 

ASSUMPTIONS (считаем истинным по умолчанию):
- ...

DECISIONS (принятые решения):
- ...

WORKS (что подтверждённо работает):
- ...

FAILS (что не работает и важно помнить):
- ...

OPEN QUESTIONS (висящие вопросы):
- ...

NEXT FOCUS (на чём дальше концентрируемся):
- ...
=== END CHECKPOINT <NAME> ===
```

### 2.1. Поля

- **`<NAME>`**  
  - Человекочитаемое имя чекпоинта, например `ZOWE_BASE_V1`.
  - Используется в строках `=== CHECKPOINT: ... ===`, `=== END HEADER: ... ===`
    и `=== END CHECKPOINT ... ===`.
  - Должно быть уникальным внутри одного чата.

- **`ID`**  
  - Числовой, **последовательный идентификатор коммита** (например `1`, `2`, `3` или `123`).
  - При создании нового чекпоинта, если пользователь явно не задаёт ID,
    ассистент выбирает следующее целое число, строго большее любого предыдущего ID
    чекпоинтов в данном чате.

- **`TIME`**  
  - Время в формате `YYYY-MM-DD HH:MM:SS`.
  - Обозначает время создания чекпоинта в часовом поясе пользователя (или максимально близкое приближение).

- **`SCOPE`**  
  - Краткое, однофразовое описание того, что фиксирует данный чекпоинт.

- **Секции тела**  
  Секции `ASSUMPTIONS`, `DECISIONS`, `WORKS`, `FAILS`, `OPEN QUESTIONS`, `NEXT FOCUS`:
  - ДОЛЖНЫ присутствовать в указанном порядке (могут быть пустыми, но заголовки должны быть).
  - Содержимое должно быть кратким и в виде списков.
  - Чекпоинт должен быть **самодостаточным**: при чтении только его одного должно быть понятно состояние проекта.

## 3. Обзор команд `chit`

`chit` поддерживает следующие подкоманды:

1. `chit commit | comm | c`  
   Создание или изменение чекпоинта.

2. `chit log`  
   Просмотр списка заголовков всех чекпоинтов  asc/desc по желанию .

3. `chit log full`  
   Просмотр списка полных текстов всех чекпоинтов asc/desc по желанию.

4. `chit log export`  
   Экспорт списка полных текстов всех чекпоинтов в файл с именем CHIT_COMMITS_<DATE>.md. Ссылка для скачивания предоставляется. Тексты отдельных чекпоинтов размещеаются внутри тегов:
   ```text
   ```

6. `chit log`  
   Просмотр списка чекпоинтов или полного текста чекпоинта по ID.

7. `chit reset`  
   Логический откат к предыдущему чекпоинту.

8. `chit -h` / `chit -help`  
   Вывод краткой справки по протоколу `chit`.

Слово `chit` ДОЛЖНО быть первым токеном в строке.

---

## 4. `chit commit` / `chit comm` / `chit c`

### 4.1. Назначение

Создать новый логический чекпоинт, суммирующий текущее состояние проекта,
или изменить (amend) **заголовок последнего чекпоинта** (имя и/или scope) без создания нового.

### 4.2. Допустимые формы

```text
chit commit [options]
chit comm [options]
chit c [options]
chit --amend [options]      # сокращённый вариант, эквивалент изменения последнего чекпоинта
```

### 4.3. Параметры

- `-n "<NAME>"`  
  Явное имя чекпоинта; попадает в `<NAME>` в заголовке и футере чекпоинта.

- `-m "<SCOPE text>"`  
  Явный текст `SCOPE`; попадает в значение строки `SCOPE:`.

- `--amend`  
  Не создавать новый чекпоинт; вместо этого **изменить последний чекпоинт** в данном чате.

  - В комбинации с `-n` меняется только имя чекпоинта.
  - В комбинации с `-m` меняется только текст описания (scope).
  - В комбинации с обоими меняются и имя, и scope.
  - **ID и TIME изменяемого чекпоинта не должны меняться**, чтобы сохранить историю.
  - Поскольку прошлые сообщения буквально редактировать нельзя, ассистент должен:
    - явно сказать, что последний чекпоинт логически изменён,
    - и, при необходимости, вывести исправленный заголовок (и scope) для ясности.

### 4.4. Поведение при отсутствии параметров

- Если `-n` не задан:
  - Ассистент выводит разумное имя `<NAME>` из контекста проекта (например `BASE_V1`, `API_DESIGN_V2`)
    или использует понятное обобщённое имя.

- Если `-m` не задан:
  - Ассистент формулирует краткий `SCOPE`, описывающий, что фиксирует чекпоинт.

- Если `--amend` не задан:
  - Создаётся новый чекпоинт с новым `ID`.

- Если **ни одного чекпоинта ещё нет**, а пользователь вызывает `chit --amend`:
  - Ассистент должен сообщить, что нет предыдущего чекпоинта для изменения,
    и предложить выполнить обычный `chit commit`.

### 4.5. Результат

При успешном `chit commit` (без `--amend`) ассистент должен вывести полный блок чекпоинта
в формате, определённом в разделе 2.

## 5. `chit log`

### 5.1. Назначение

Показать список известных чекпоинтов в текущем чате, не изменяя логическое состояние проекта.

### 5.2. Допустимые формы

```text
chit log
chit log -<n>
chit log -ID <ID>
```

### 5.3. Параметры

- `-<n>`  
  - `n` — положительное целое число.  
  - Показать только последние `n` чекпоинтов, начиная с самого нового из тех, которые сейчас считаются активными.

- `-ID <ID>`  
  - Показать **полный блок чекпоинта** (от `=== CHECKPOINT` до `=== END CHECKPOINT`)
    для чекпоинта с заданным числовым `ID`.
  - Если среди **активных** чекпоинтов такого ID нет, ассистент должен об этом сообщить.

### 5.4. Формат вывода

- Без параметров `chit log` выводит по одному чекпоинту в строке:

  ```text
  <ID>: <NAME>
  <ID>: <NAME>
  ...
  ```

- `chit log -<n>` выводит до `n` последних активных чекпоинтов в том же формате.

- `chit log -ID <ID>` выводит полный блок чекпоинта с этим ID.

### 5.5. Правило контекста

`chit log` — **операция только чтения**:

- Не должен вводить новые предположения, решения или чекпоинты.
- Не должен менять набор активных чекпоинтов.  
- Должен рассматриваться как “только просмотр истории”.

---

## 6. `chit reset`

### 6.1. Назначение

Логически откатить состояние проекта к конкретному чекпоинту.

Это **не** удаляет сообщения из чата, но изменяет:

- какие чекпоинты считаются **активными**,
- что будет видеть `chit log`.

### 6.2. Допустимые формы

```text
chit reset
chit reset -ID <ID>
```

### 6.3. Поведение

- `chit reset` (без параметров):
  - Откат к **последнему активному чекпоинту** (с максимальным ID среди активных).
  - Это может фактически отбросить более поздние “незакоммиченные” рассуждения
    в терминах того, что считается валидным состоянием.

- `chit reset -ID <ID>`:
  - Откат к чекпоинту с заданным числовым ID.
  - После этой операции:
    - `chit log` должен видеть только чекпоинты **с начала чата до этого ID включительно**.
    - Все чекпоинты с ID больше `<ID>` становятся **логически неактивными**
      (они остаются в тексте, но не должны появляться в `chit log` и не должны использоваться как базовое состояние).

Если чекпоинта с таким ID среди известных нет, ассистент должен об этом сообщить и не выполнять откат.

### 6.4. Рассуждения после reset

После reset ассистент должен:

- Считать выбранный чекпоинт **текущей базой состояния**.
- Игнорировать любые противоречащие решения, предположения и выводы, которые происходят из неактивных чекпоинтов.
- Использовать следующие инструкции пользователя, чтобы двигаться дальше от этой базы.

## 7. `chit -h` / `chit -help`

### 7.1. Назначение

Вывести краткий текст помощи по протоколу `chit`.

### 7.2. Допустимые формы

```text
chit -h
chit -help
```

### 7.3. Содержание

Текст помощи должен кратко описывать:

1. Назначение `chit` (логические коммиты / чекпоинты в чате).
2. Доступные подкоманды:
   - `chit commit | comm | c` с параметрами `-n`, `-m`, `--amend`
   - `chit log` с параметрами `-<n>`, `-ID <ID>`
   - `chit reset` с опциональным `-ID <ID>`
   - `chit -h` / `chit -help`
3. Напоминание о том, что:
   - `chit` должен стоять в начале строки,
   - чекпоинты имеют фиксированный формат,
   - `chit log` не должен менять текущий логический контекст,
   - `chit reset` меняет набор активных чекпоинтов.

---

## 8. Использование `chit` в новых проектах или чатах

Чтобы надёжно использовать этот протокол в новом чате:

1. Пользователь может вставить:
   - либо эту полную спецификацию,
   - либо короткий “активационный сниппет”, суммирующий правила.

2. Как только ассистент понимает, что в данном чате используется `chit`, он должен:
   - интерпретировать любую строку, начинающуюся с `chit`, как команду согласно этому документу,
   - вести внутренний список чекпоинтов для этого чата,
   - соблюдать семантику `commit`, `log` и `reset`, описанную выше.

3. Все логические коммиты / чекпоинты в чате являются инструкциями только для текщего чата и невидимы для других чатов. Нумерация 
   коммитов ведется в каждом чате отдельно. Команда `chit reset` действует только на текущий чат. 

Если поведение неоднозначно, ассистент должен уточнить намерения пользователя, но держать
данную спецификацию основным источником правил.
